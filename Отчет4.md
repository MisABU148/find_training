# Отчёт по лабораторной работе: сбор метрик приложения с VictoriaMetrics

## 1. Цель работы

Развернуть VictoriaMetrics в кластере Minikube, где работает приложение из ДЗ №1, настроить экспорт метрик рантайма, PostgreSQL и бизнес-метрик приложения в формате Prometheus/OpenMetrics и организовать их автоматический сбор через service discovery по аннотациям `prometheus.io/*`.

## 2. Используемые технологии

- **Kubernetes / Minikube** — запуск и управление контейнеризированным приложением.
- **Helm** — установка VictoriaMetrics.
- **VictoriaMetrics Single** — хранение метрик и их сбор по pull-модели.
- **Spring Boot Actuator + Micrometer** — метрики рантайма (JVM, HTTP, пул соединений) и бизнес-метрики.
- **micrometer-registry-prometheus** — вывод метрик в формате Prometheus.
- **postgres-exporter** — метрики PostgreSQL.
- **PostgreSQL** — база данных приложения.

## 3. Архитектура решения

Приложение и система мониторинга развёрнуты в одном кластере Minikube. Приложение состоит из frontend, backend и PostgreSQL, компоненты VictoriaMetrics размещены в отдельном namespace `monitoring`.

Метрики собираются по pull-модели. VictoriaMetrics находит поды с аннотациями `prometheus.io/*` (service discovery) и периодически опрашивает их HTTP-эндпоинты.

Поток данных:

`Backend (/actuator/prometheus) ─┐`
`PostgreSQL → postgres-exporter (/metrics) ─┴→ VictoriaMetrics`

## 4. Развёртывание VictoriaMetrics

Обновлён список чартов и создан namespace:

```bash
helm repo update
kubectl create namespace monitoring
```

VictoriaMetrics Single установлена командой:

```bash
helm install vm-single vm/victoria-metrics-single \
  -n monitoring \
  --set server.scrape.enabled=true
```

Состояние компонентов проверялось командами:

```bash
kubectl get pods -n monitoring
kubectl get svc -n monitoring
```

Поды VictoriaMetrics находятся в состоянии `Running`.

## 5. Доступ к интерфейсу

Для доступа к VictoriaMetrics выполнен проброс порта:

```bash
kubectl port-forward svc/vm-single-victoria-metrics-single-server \
  -n monitoring 8428:8428
```

API доступен по адресу http://localhost:8428, запросы выполнялись через `curl`.

## 6. Метрики рантайма

В `pom.xml` бэкенда добавлены зависимости `spring-boot-starter-actuator` и `micrometer-registry-prometheus`, а в `application.yml` открыт эндпоинт Prometheus:

```yaml
management:
  endpoints:
    web:
      exposure:
        include: health,prometheus
```

Эндпоинт `/actuator/prometheus` отдаёт метрики JVM (`jvm_memory_used_bytes`, `jvm_gc_*`), HTTP-запросов (`http_server_requests_seconds_*`) и пула соединений Hikari.

## 7. Метрики PostgreSQL

В Deployment postgres добавлен второй контейнер `postgres-exporter` (`quay.io/prometheuscommunity/postgres-exporter`), порт 9187. Контейнеры пода делят сетевое пространство, поэтому exporter подключается к базе по адресу `localhost:5432`. Логин, пароль и имя БД берутся из Secret `postgres-secret` и ConfigMap `app-config`, в манифесте они не хранятся. Ключевая метрика состояния: `pg_up`.

## 8. Бизнес-метрики

Все метрики объявлены в одном компоненте `BusinessMetrics` (пакет `metrics`), который внедряется в сервисы приложения.

| Метрика | Тип | Что считает |
|---|---|---|
| `training_slot_added_total` | Counter | созданные слоты тренировок |
| `training_slot_booked_total` | Counter | успешные записи на тренировку |
| `training_slot_cancelled_total` | Counter | отмены записи |
| `training_slot_booking_failed_total{reason}` | Counter | неудачные записи, причина в теге `reason` |
| `training_slots_free` | Gauge | текущее число свободных слотов |
| `training_slots_booked` | Gauge | текущее число забронированных слотов |
| `training_slot_booking_duration` | Timer | время выполнения записи на слот |
| `user_registered_total` | Counter | регистрации пользователей |
| `user_login_success_total` | Counter | успешные входы |
| `user_login_failed_total` | Counter | неуспешные входы |

Счётчики накапливают историю событий и обнуляются при перезапуске пода, поэтому для анализа используются функции `rate()` и `increase()`. Gauge считаются напрямую по базе и отражают текущее состояние, в том числе сами учитывают отмены записей.

## 9. Service discovery

В Deployment бэкенда и postgres в `spec.template.metadata` добавлены аннотации.

Backend:

```yaml
annotations:
  prometheus.io/scrape: "true"
  prometheus.io/port: "8080"
  prometheus.io/path: "/actuator/prometheus"
```

PostgreSQL (порт exporter):

```yaml
annotations:
  prometheus.io/scrape: "true"
  prometheus.io/port: "9187"
  prometheus.io/path: "/metrics"
```

VictoriaMetrics находит такие поды (job `kubernetes-pods`) и собирает метрики автоматически, при пересоздании пода цель обновляется сама.

## 10. Проверка сбора метрик

### 10.1. Доступность целей

```bash
curl "http://localhost:8428/api/v1/query?query=up"
```

Запрос возвращает статус всех целей сбора. В job `kubernetes-pods` присутствуют под бэкенда (`10.244.0.59:8080`) и под postgres (`10.244.0.58:9187`), у обоих значение `1`. Это подтверждает, что service discovery по аннотациям работает.

### 10.2. Метрика PostgreSQL

```bash
curl "http://localhost:8428/api/v1/query?query=pg_up"
```

Значение `1` означает, что exporter успешно подключён к базе данных.

### 10.3. Бизнес-метрики

```bash
curl "http://localhost:8428/api/v1/query?query=training_slot_booked_total"
curl "http://localhost:8428/api/v1/query?query=training_slots_free"
```

Запросы возвращают текущие значения счётчика записей и числа свободных слотов. Значения менялись после действий в приложении (создание слота, запись, отмена).

### 10.4. Скорость событий

```text
increase(training_slot_booked_total[10m])
rate(training_slot_booking_failed_total[5m])
```

Первый запрос показывает число записей за 10 минут, второй скорость неудачных записей. Такие запросы пригодятся для дашбордов и алертов в следующих работах.

## 11. Проверка состояния компонентов

Для проверки приложения и мониторинга использовались команды:

```bash
kubectl get pods
kubectl get pods -n monitoring
kubectl get svc -n monitoring
```

Под postgres находится в состоянии `Running` с `READY 2/2` (база и exporter), бэкенд и поды VictoriaMetrics в состоянии `Running`. Демонстрация приложена в виде скринкаста.

## 12. Вывод

В кластере Minikube развёрнута VictoriaMetrics Single. Бэкенд экспортирует метрики рантайма и бизнес-метрики через Actuator и Micrometer, PostgreSQL через postgres-exporter. Сбор выполняется автоматически по аннотациям `prometheus.io/*`, цели подтверждены запросом `up`. Реализованные бизнес-метрики покрывают успешные и неуспешные операции, текущее состояние и время выполнения, и будут использованы в следующих работах.
