# Отчёт

## Доменная область

Приложение **Find Training** (кодовое имя `coach-app`) — сервис для поиска тренировок: пользователи ищут
тренажёрные залы и персональных тренеров, тренеры привязаны к залу и специализируются на конкретных видах
спорта. В базовой версии реализованы: саморегистрация пользователей, справочник видов спорта, каталог залов и
каталог тренеров с привязкой к залу и списком видов спорта, которые они ведут.

## Стек реализации

**Бэкенд**
- Java 25, Spring Boot 4.1.1 (`spring-boot-starter-webmvc`, `spring-boot-starter-data-jpa`,
  `spring-boot-starter-validation`)
- Hibernate / JPA — ORM
- PostgreSQL 16 — СУБД
- Flyway (`flyway-core` + `flyway-database-postgresql`) — миграции схемы БД
- Lombok — сокращение boilerplate-кода
- `spring-security-crypto` (BCrypt) — хэширование паролей (без полноценного Spring Security — авторизация
  через JWT вынесена в отдельный этап)
- SLF4J / Logback — логирование
- Maven — сборка

**Фронтенд**
- React 19 + Vite 8 (JavaScript, без TypeScript)
- react-router-dom — маршрутизация
- Fetch API — HTTP-клиент к бэкенду (прокси `/api` → `http://localhost:8080` в dev-режиме)

**Инфраструктура (для разработки)**
- Docker Compose — локальный контейнер PostgreSQL (сам бэкенд и фронтенд пока запускаются напрямую, без
  контейнеризации — это отдельный этап следующих домашних заданий)

Выбор стека продиктован советом задания использовать нересурсоёмкое окружение: Spring Boot поднимается за
секунды, Vite — мгновенный dev-сервер, а взаимодействие клиент-сервер идёт по обычному HTTP/1.1 REST (JSON),
без gRPC.

## Основные сущности доменной области

| Сущность | Поля | Связи |
|---|---|---|
| **User** | id, fullName, email (уникальный), password (хэш), phone, role (USER/COACH/ADMIN), createdAt | — |
| **Gym** (зал) | id, name, address, city, phone, description, createdAt | один зал — много тренеров |
| **Sport** (вид спорта) | id, name (уникальное) | многие-ко-многим с Coach |
| **Coach** (тренер) | id, fullName, email (уникальный), phone, bio, experienceYears, createdAt | ManyToOne → Gym (опционально), ManyToMany → Sport |

CRUD-операции:
- **User** — полный CRUD (`GET/POST/PUT/DELETE /api/users`) + отдельный публичный `POST /api/auth/register`
  (саморегистрация всегда создаёт роль `USER`, без права выбрать её самому).
- **Gym** — полный CRUD (`GET/POST/PUT/DELETE /api/gyms`).
- **Coach** — полный CRUD (`GET/POST/PUT/DELETE /api/coaches`), включая привязку к залу и видам спорта.
- **Sport** — намеренно урезанный CRUD: только список, добавление и удаление (`GET/POST/DELETE /api/sports`,
  без `PUT`) — это справочник, редактирование названия не требуется по логике приложения.

## Соответствие методологии 12 факторов

**I. Codebase (кодовая база)** — один git-репозиторий содержит и `backend/`, и `frontend/`; общего кода между
ними нет, каждый деплоится независимо из одной и той же кодовой базы. *Соответствует.*

**II. Dependencies (зависимости)** — зависимости бэкенда явно объявлены в `pom.xml` (Maven сам изолирует их в
локальном репозитории), зависимости фронтенда — в `package.json` с зафиксированными версиями в
`package-lock.json`. Ни одна зависимость не предполагается «уже стоящей в системе». *Соответствует.*

**III. Config (конфигурация)** — все специфичные для окружения параметры (адрес и логин БД, порт сервера, JWT-
секрет, уровни логирования) вынесены в переменные окружения и подставляются в `application.yaml` через
`${VAR}`; ничего из этого не зашито в код. Реальный `.env` добавлен в `.gitignore` и никогда не попадает в git,
а `.env.example` документирует нужные ключи плейсхолдерами. *Соответствует.*

**IV. Backing services (внешние сервисы)** — PostgreSQL подключается как присоединяемый ресурс по URL
(`DB_URL`/`DB_USERNAME`/`DB_PASSWORD`); замена на другой инстанс БД (или провайдера) требует правки только
переменных окружения, без изменения кода. *Соответствует.*

**V. Build, release, run (сборка, релиз, запуск)** — собранный артефакт (jar бэкенда через `mvn package`,
статическая сборка фронтенда через `npm run build`) не содержит зашитой конфигурации окружения — вся она
подставляется в момент запуска через env. Формально отдельного CI/CD-пайплайна с разделёнными стадиями
build/release/run пока нет — это осознанно отложено на этап контейнеризации в одном из следующих домашних
заданий. *Частично соответствует: разделение конфигурации и артефакта есть, автоматизации стадий — нет.*

**VI. Processes (процессы)** — бэкенд не хранит состояние между запросами: нет HTTP-сессий, нет in-memory кэшей
с бизнес-данными, всё состояние — в PostgreSQL. Фронтенд — статичный SPA без серверного состояния. Это же
заложено на будущее для JWT (токен вместо серверной сессии). *Соответствует.*

**VII. Port binding (привязка к порту)** — бэкенд самодостаточен (embedded Tomcat из Spring Boot) и публикует
себя через `SERVER_PORT` (настраивается через env), внешний контейнер сервлетов не нужен. Фронтенд в проде
должен будет отдаваться отдельным лёгким статик-сервером/прокси со своим портом — это не реализовано, так как
контейнеризация фронтенда прямо вынесена за рамки этого задания. *Частично соответствует: бэкенд — полностью,
прод-раздача фронтенда — не реализована по согласованию с условием задания.*

**VIII. Concurrency (конкурентность)** — масштабирование предполагается через запуск нескольких stateless-
инстансов бэкенда за балансировщиком (тема следующего домашнего задания); внутри одного процесса конкурентность
регулируется пулом потоков Tomcat (`SERVER_THREADS_MAX`) и пулом соединений к БД (`DB_POOL_MAX`/`DB_POOL_MIN`),
оба — через env. Общего изменяемого состояния в процессе, мешающего горизонтальному масштабированию, нет.
*Соответствует.*

**IX. Disposability (одноразовость)** — `server.shutdown: graceful` и
`spring.lifecycle.timeout-per-shutdown-phase` дают приложению корректно завершить обрабатываемые запросы и
закрыть пул соединений с БД при остановке; старт быстрый — тяжёлого прогрева нет, миграции Flyway выполняются
один раз при старте. *Соответствует.*

**X. Dev/prod parity (паритет окружений)** — и локально, и в любом другом окружении используется один и тот же
backing service — настоящий PostgreSQL (не подменяется на H2 для скорости), и один и тот же механизм миграций
(Flyway); локально Postgres поднимается через `docker-compose.yml`, но сама СУБД идентична той, что будет в
проде. *Соответствует.*

**XI. Logs (логи)** — приложение никогда не пишет логи в файлы самостоятельно: SLF4J/Logback выводит всё в
stdout единым текстовым потоком (`logging.pattern.console`), уровни настраиваются через
`LOG_LEVEL_ROOT`/`LOG_LEVEL_APP`. Куда дальше собирать и агрегировать этот поток — решает среда выполнения, а
не сама программа. *Соответствует.*

**XII. Admin processes (административные процессы)** — единственная административная задача приложения —
миграции схемы БД — выполняется самим приложением через Flyway при старте, в той же кодовой базе и с той же
конфигурацией, что и обычный запуск; отдельного ручного скрипта или консоли с другим окружением не существует.
*Соответствует.*
