# Отчёт по лабораторной работе: SLI, SLO и SLA

## 1. Цель работы

На основе метрик из ДЗ №4 сформулировать SLI, SLO и SLA для приложения записи на тренировки, реализовать пробер, построить графики в vmui и показать, как они меняются при изменении поведения приложения.

## 2. Используемые технологии

- **VictoriaMetrics Single + vmui** — хранение метрик и построение графиков (MetricsQL).
- **Spring Boot Actuator + Micrometer** — HTTP-метрики и бизнес-метрики.
- **postgres-exporter** — метрика `pg_up`.
- **Пробер (Python)** — проверка доступности бэкенда «снаружи».
- **Kubernetes / Minikube** — запуск приложения, пробера и мониторинга.

## 3. Выбранные метрики

| Метрика | Тип | Что показывает |
|---|---|---|
| `http_server_requests_seconds_count{status}` | Counter | число HTTP-запросов, статус в теге |
| `http_server_requests_seconds_bucket{le}` | Histogram | распределение времени ответа |
| `training_slot_booked_total` | Counter | успешные записи на тренировку |
| `training_slot_booking_failed_total{reason}` | Counter | неудачные записи; `reason` — причина (`already_booked`, `slot_in_past`, `time_conflict` и др.) |
| `pg_up` | Gauge | подключение postgres-exporter к БД (1/0) |
| `probe_success` | Gauge | результат проверки пробера (1/0) |
| `probe_duration_seconds` | Gauge | время ответа бэкенда для пробера |

Все запросы к метрикам бэкенда выбираются по `job="kubernetes-pods"`. Служебный трафик `/actuator/*` исключён (`uri!~"/actuator.*"`), чтобы сбор метрик и проверки не искажали статистику.

## 4. SLI, SLO и SLA

Окно для SLO и SLA — 30 дней. В демонстрации окна сокращены, чтобы изменения были видны на графиках: `[1m]` для SLI-1 и SLI-2, `[5m]` для SLI-3 (записей мало, на `[1m]` график слишком скачет) и `[5m:1m]` для SLI-4.

| SLI | Тип | Формула | SLO | SLA |
|---|---|---|---|---|
| SLI-1. Доступность | RBSLO | `1 − запросы_5xx / все_запросы` | ≥ 99,5% | ≥ 99% |
| SLI-2. Латентность | RBSLO | `запросы_быстрее_1с / все_запросы` | ≥ 95% | ≥ 90% |
| SLI-3. Успешность записей | RBSLO | `booked / (booked + failed)` | ≥ 99% | ≥ 97% |
| SLI-4. Доступность по времени | TBSLO | `хорошие_минуты / все_минуты` | ≥ 99,5% | ≥ 99% |

SLA установлен мягче SLO, так как SLA не может быть выше подтверждённого SLO.

В `failed` входят все причины неуспешной записи: `already_booked`, `slot_in_past`, `time_conflict` и др. Ошибки пользователя (ответ 4xx) тоже считаются неуспешными записями. На SLI-1 они не влияют, так как он учитывает только ответы 5xx.

### Запросы

**SLI-1:**

```promql
1 - (
  (sum(rate(http_server_requests_seconds_count{job="kubernetes-pods",uri!~"/actuator.*",status=~"5.."}[1m])) or vector(0))
  /
  sum(rate(http_server_requests_seconds_count{job="kubernetes-pods",uri!~"/actuator.*"}[1m]))
)
```

**SLI-2:**

```promql
sum(rate(http_server_requests_seconds_bucket{job="kubernetes-pods",uri!~"/actuator.*",le="1.0"}[1m]))
/
sum(rate(http_server_requests_seconds_count{job="kubernetes-pods",uri!~"/actuator.*"}[1m]))
```

**SLI-3:**

```promql
sum(increase(training_slot_booked_total{job="kubernetes-pods"}[5m]))
/
(
  sum(increase(training_slot_booked_total{job="kubernetes-pods"}[5m]))
  + (sum(increase(training_slot_booking_failed_total{job="kubernetes-pods"}[5m])) or vector(0))
)
```

Разбивка неудач по причинам:

```promql
sum by (reason)(increase(training_slot_booking_failed_total{job="kubernetes-pods"}[5m]))
```

**SLI-4** (минута хорошая, если одновременно пробер успешен и БД доступна):

```promql
avg_over_time((min(probe_success) * min(pg_up))[5m:1m])
```

**Линии SLO и SLA на графиках:**

| SLI | SLO | SLA |
|---|---|---|
| SLI-1, SLI-4 | `vector(0.995)` | `vector(0.99)` |
| SLI-2 | `vector(0.95)` | `vector(0.90)` |
| SLI-3 | `vector(0.99)` | `vector(0.97)` |

### Error budget

```
error_budget_remaining = 1 − (1 − SLI) / (1 − SLO)
```

Значение ниже 0 означает, что бюджет исчерпан. Запрос для SLI-1:

```promql
1 - (1 - (
  1 - (
    (sum(rate(http_server_requests_seconds_count{job="kubernetes-pods",uri!~"/actuator.*",status=~"5.."}[1m])) or vector(0))
    /
    sum(rate(http_server_requests_seconds_count{job="kubernetes-pods",uri!~"/actuator.*"}[1m]))
  )
)) / (1 - 0.995)
```

Для SLO 99,5% бюджет за 30 дней — 0,5% запросов или ≈ 3,6 часа простоя. Для SLA 99% допустимый простой ≈ 7,2 часа.

### Общий SLA

> Сервис доступен не менее 99% времени в месяц, не менее 90% запросов обрабатываются быстрее 1 секунды, не менее 97% попыток записи на тренировку завершаются успешно.

## 5. Изменения приложения для демонстрации

1. **Гистограмма задержек.** В `application.yml` включены бакеты `http.server.requests` (`percentiles-histogram` и `slo: 100ms,500ms,1s,2s`), чтобы считать долю быстрых запросов.
2. **Пробер.** Deployment `prober` (скрипт Python в ConfigMap, манифест лежит в каталоге `k8s/backend`) раз в 10 секунд запрашивает `GET http://backend:8080/api/training-slots?gymId=3` (сервис `backend`, ClusterIP, порт 8080) и отдаёт `probe_success` и `probe_duration_seconds`. Под размечен аннотациями `prometheus.io/*`, VictoriaMetrics собирает его автоматически.
3. **Управляемая деградация.** Добавлен `FaultInjectionFilter` с эндпоинтами `/api/debug/errors?percent=N` (доля ответов 500) и `/api/debug/delay?ms=N` (задержка ответа). Это демонстрационный механизм.
4. **Нагрузка** (`kubectl port-forward svc/backend 8090:8080`, три цикла `curl` в cmd):
   - запись и отмена слота 9 пользователем 3 создают успешные бизнес-операции (`training_slot_booked_total`);
   - `GET /api/training-slots?gymId=3` каждые 2 секунды даёт постоянный трафик для SLI-1 и SLI-2;
   - повторная запись на уже занятый слот 6 даёт ответ 409 и причину `already_booked` в `training_slot_booking_failed_total` (включается отдельно, на шаге 6).
5. **Остановка БД:** `kubectl scale deploy postgres --replicas=0`, запуск: `--replicas=1`.
6. **Исправления из ДЗ №4:** персональные данные (email) убраны из логов, счётчик слотов переименован (`training_slot_added`, суффикс `_created` зарезервирован в OpenMetrics), в `bookingFailed` учтены все причины неудачных записей, в коллекторе логов задан `msgField: message`.

## 6. Вывод

Для приложения определены четыре SLI (три по запросам и один по времени), для каждого заданы SLO и SLA и формулы расчёта. Пробер и метрики VictoriaMetrics показывают нарушение SLO при деградации приложения: ошибках, задержках, неудачных бизнес-операциях и недоступности БД. Изменение графиков при деградации приложения (ошибки 500, задержка, неудачные записи, остановка БД) показано в приложенном скринкасте. Подход будет использован для дашбордов и алертов в следующих работах.
