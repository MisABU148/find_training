# Отчёт по лабораторной работе: SLI, SLO и SLA

## 1. Цель работы

На основе метрик из ДЗ №4 сформулировать SLI, SLO и SLA для приложения записи на тренировки, реализовать пробер, построить графики в vmui и показать, как они меняются при изменении поведения приложения.

## 2. Используемые технологии

- **VictoriaMetrics Single + vmui** — хранение метрик и построение графиков (MetricsQL).
- **Spring Boot Actuator + Micrometer** — HTTP-метрики и бизнес-метрики.
- **postgres-exporter** — метрика `pg_up`.
- **Пробер (Python)** — проверка доступности бэкенда «снаружи».
- **Kubernetes / Minikube** — запуск приложения, пробера и мониторинга.

## 3. Выбранные метрики

| Метрика | Тип | Что показывает |
|---|---|---|
| `http_server_requests_seconds_count{status}` | Counter | число HTTP-запросов, статус в теге |
| `http_server_requests_seconds_bucket{le}` | Histogram | распределение времени ответа |
| `training_slot_booked_total` | Counter | успешные записи на тренировку |
| `training_slot_booking_failed_total{reason}` | Counter | неудачные записи с причиной |
| `pg_up` | Gauge | подключение postgres-exporter к БД (1/0) |
| `probe_success` | Gauge | результат проверки пробера (1/0) |

Все запросы к метрикам бэкенда выбираются по `job="kubernetes-pods"`. Служебный трафик `/actuator/*` исключён (`uri!~"/actuator.*"`), чтобы сбор метрик и проверки не искажали статистику.

## 4. SLI, SLO и SLA

Окно для SLO и SLA — 30 дней. В демонстрации используется окно 5 минут, чтобы изменения были видны на графиках.

| SLI | Тип | Формула | SLO | SLA |
|---|---|---|---|---|
| SLI-1. Доступность | RBSLO | `1 − запросы_5xx / все_запросы` | ≥ 99,5% | ≥ 99% |
| SLI-2. Латентность | RBSLO | `запросы_быстрее_1с / все_запросы` | ≥ 95% | ≥ 90% |
| SLI-3. Успешность записей | RBSLO | `booked / (booked + failed)` | ≥ 99% | ≥ 97% |
| SLI-4. Доступность по времени | TBSLO | `хорошие_минуты / все_минуты` | ≥ 99,5% | ≥ 99% |

SLA установлен мягче SLO, так как SLA не может быть выше подтверждённого SLO.

### Запросы

**SLI-1:**

```promql
1 - (
  (sum(rate(http_server_requests_seconds_count{job="kubernetes-pods",uri!~"/actuator.*",status=~"5.."}[5m])) or vector(0))
  /
  sum(rate(http_server_requests_seconds_count{job="kubernetes-pods",uri!~"/actuator.*"}[5m]))
)
```

**SLI-2:**

```promql
sum(rate(http_server_requests_seconds_bucket{job="kubernetes-pods",uri!~"/actuator.*",le="1.0"}[5m]))
/
sum(rate(http_server_requests_seconds_count{job="kubernetes-pods",uri!~"/actuator.*"}[5m]))
```

**SLI-3:**

```promql
sum(increase(training_slot_booked_total{job="kubernetes-pods"}[5m]))
/
(
  sum(increase(training_slot_booked_total{job="kubernetes-pods"}[5m]))
  + (sum(increase(training_slot_booking_failed_total{job="kubernetes-pods"}[5m])) or vector(0))
)
```

**SLI-4** (минута хорошая, если пробер успешен и БД доступна):

```promql
avg_over_time(min(probe_success)[5m:1m]) * avg_over_time(min(pg_up)[5m:1m])
```

**Линии SLO и SLA на графиках:** `vector(0.995)` и `vector(0.99)`.

### Error budget

```
error_budget_remaining = 1 − (1 − SLI) / (1 − SLO)
```

Для SLO 99,5% бюджет за 30 дней — 0,5% запросов или ≈ 3,6 часа простоя. Для SLA 99% допустимый простой ≈ 7,2 часа.

### Общий SLA

> Сервис доступен не менее 99% времени в месяц, не менее 90% запросов обрабатываются быстрее 1 секунды, не менее 97% попыток записи на тренировку завершаются успешно.

## 5. Изменения приложения для демонстрации

1. **Гистограмма задержек.** В `application.yml` включены бакеты `http.server.requests` (`percentiles-histogram` и `slo: 100ms,500ms,1s,2s`), чтобы считать долю быстрых запросов.
2. **Пробер.** Deployment `prober` (скрипт Python в ConfigMap) раз в 10 секунд запрашивает `GET /api/training-slots?gymId=1` у бэкенда и отдаёт `probe_success` и `probe_duration_seconds`. Под размечен аннотациями `prometheus.io/*`, VictoriaMetrics собирает его автоматически.
3. **Управляемая деградация.** Добавлен `FaultInjectionFilter` с эндпоинтами `/api/debug/errors?percent=N` (доля ответов 500) и `/api/debug/delay?ms=N` (задержка ответа). Это демонстрационный механизм.
4. **Нагрузка.** Цикл `curl` к API создаёт постоянный трафик, а отдельный цикл «запись и отмена» создаёт бизнес-операции. Попытки записи на занятый слот дают ошибки `already_booked` в `training_slot_booking_failed_total`.
5. **Остановка БД:** `kubectl scale deploy postgres --replicas=0`.

## 6. Сценарий и результаты

| № | Действие | Затронутый SLI | Ожидание | Результат |
|---|---|---|---|---|
| 1 | Штатная работа под нагрузкой | все | SLI ≈ 100%, выше SLO | *(заполнить)* |
| 2 | Ошибки 500 (`percent=30`) | SLI-1 | падение ниже SLO и SLA, расход бюджета | *(заполнить)* |
| 3 | Ошибки выключены (`percent=0`) | SLI-1 | восстановление | *(заполнить)* |
| 4 | Задержка 1500 мс | SLI-2 | падение ниже SLO | *(заполнить)* |
| 5 | Задержка выключена | SLI-2 | восстановление | *(заполнить)* |
| 6 | Запись на занятый слот | SLI-3 | падение доли успешных записей | *(заполнить)* |
| 7 | Остановка БД | SLI-4, SLI-1 | `pg_up` и `probe_success` = 0, SLI-4 падает | *(заполнить)* |
| 8 | Запуск БД | SLI-4, SLI-1 | восстановление | *(заполнить)* |

Демонстрация приложена в виде скринкаста.

## 7. Вывод

Для приложения определены четыре SLI (три по запросам и один по времени), для каждого заданы SLO и SLA и формулы расчёта. Пробер и метрики VictoriaMetrics показывают нарушение SLO при деградации приложения: ошибках, задержках, неудачных бизнес-операциях и недоступности БД. Подход будет использован для дашбордов и алертов в следующих работах.
